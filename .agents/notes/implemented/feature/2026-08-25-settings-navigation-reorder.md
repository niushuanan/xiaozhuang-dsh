# Agent Note: Hold-to-reorder settings navigation

Status: implemented

English | [中文](2026-08-25-settings-navigation-reorder.zh.md)

## Problem

The settings shell orders every section by the `order` value on its `settings.section` registration. That order is useful as the product default but gives a user with frequently visited plugin pages no way to place those pages together. An explicit customization page or persistent edit mode would add controls and state to a navigation that otherwise needs only direct manipulation.

A short settings list also leaves most of the rail empty. Pointer coordinates in that empty space must still resolve to the actual first or last insertion point; treating the panel height as a list of possible positions would produce invisible or unreachable order slots.

## Decision

The existing `ui-settings-general` native plugin owns navigation reordering because it already owns the `sidebar.settings` entry, projects every section row, and renders the rail. The entry declares one root-scoped store containing only the ordered section ids. The renderer reconciles that preference against the live section ledger: saved ids that still exist come first, newly registered ids append in normal plugin order, and absent ids are ignored.

A primary-pointer press held for one second starts a drag. Movement before the hold threshold cancels the gesture so ordinary clicks retain their existing behavior. During a drag, the shell compares the pointer's vertical coordinate with the center of each real row except the held row. A coordinate above every center maps to index zero; one below every center maps after the final row. This clamp makes the whole empty area below a short list a usable route to the final real position without inventing blank positions.

The rail renders one two-pixel insertion line at the resolved boundary and dims the held row. Pointer capture keeps the gesture continuous outside the row. Releasing writes the complete visible id order and suppresses the click generated by that same pointer sequence; there is no edit mode, reorder button, confirmation step, or separate settings page.

## Alternatives considered

**A dedicated navigation-customization page or edit toggle.** Rejected because it adds a mode, controls, copy, and an extra save path to a task that direct manipulation completes in one gesture.

**HTML drag and drop.** Rejected because its browser-native feedback and touch behavior vary, while pointer events provide the same mouse and touch geometry and let the product own the insertion line.

**Persisting replacement `order` values into each feature registration.** Rejected because one shell interaction must not mutate plugin-owned registrations. A shell-owned list of ids overlays the live ledger without changing feature packages or registration contracts.

## Consequences

Users can arrange all currently visible settings sections, including third-party plugin pages, and the order survives panel remounts and browser reloads. Dynamic plugin removal and addition remain safe because the preference is reconciled rather than treated as a complete registry. The preference is browser-local viewing state; it does not alter `settings.yaml`, plugin configuration, model input, or KV-cache behavior.

The component coverage pins the one-second threshold, the single insertion marker, clamping to both real list ends, and persistence across remount. The assembled browser remains the visual check for pointer capture, line placement, and unchanged click navigation.
