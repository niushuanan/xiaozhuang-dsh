# Agent Note: 可逆的输入框添加菜单

Status: implemented

[English](2026-08-23-composer-add-menu.md) | 中文

## Problem

输入框左下角的常驻加号会直接打开完整命令目录，但消息输入框旁的加号通常表示添加文件或其他常用输入。这让第一次点击违背直觉，也使已有图片接收链路只能通过粘贴和拖拽发现。直接替换命令目录会损失有价值的高级操作，而再常驻一个按钮又会增加每个对话的工具栏噪声。

## Decision

`ui-conversation` 在输入框工具栏首位声明单占用的 `conversation.input.add` slot。`InputBar` 通过普通 owner props 传递原生图片接收回调、支持的媒体类型、命令目录开关、当前命令菜单状态、锁定状态和输入框焦点恢复回调。没有插件占用时，slot 渲染 `ComposerCommandAction`，保留原来的“加号打开命令”行为，也保留同一个 textarea DOM。

Web profile 的 `composer-add-menu` 插件用一个紧凑的双操作菜单占用该 slot。“添加文件”打开浏览器文件选择器，并把选中的图片交给与粘贴、拖拽相同的 `intakeImages` 校验和草稿附件链路；“运行命令”打开已有命令目录，不复制命令目录或调度逻辑。点击外部或按 Escape 会关闭紧凑菜单。「小庄的插件」开关挂载或卸载这个占用项，因此关闭插件后会立即露出原生 fallback。

## Alternatives considered

**维持加号作为命令快捷方式。** 否决，因为图标和位置表达的是添加内容，而不是打开高级命令目录。

**用文件选择器完全替代命令。** 否决，因为命令发现仍有价值，而且用户明确要求保留命令。

**分别常驻文件与命令按钮。** 否决，因为常用链路只需要一次短点击，两个常驻控件会占用窄窗口里宝贵的输入框空间。

**新建第二套上传服务。** 否决，因为原生草稿图片服务已经负责类型与大小限制、预览、移除、提交和持久附件准入。

## Consequences

启用插件后，加号菜单第一项是文件选择，命令只多一步。当前 Host 仍只接收图片附件，因此菜单会明确说明选择的是图片文件，不承诺任意文档上传。这个 slot 是一个小型公开组合接缝：后续插件可以替换添加菜单的呈现，但必须复用所提供的回调，不得直接访问 conversation service 或复制附件状态。

## Verification

组件测试保留原生命令 fallback 与选择区间转发，profile 契约测试固定 slot 接管、两项操作和关闭行为。组装后的 Web 路径会打开紧凑菜单，通过真实文件选择器选择本地 PNG，观察原生待发送图片栏，再移除验收图片；随后打开未改变的命令目录，通过设置关闭插件确认原生命令入口恢复，再在不重载对话的情况下重新开启插件。
