# Agent Note: 原生持续适配

Status: implemented

[English](2026-08-26-native-adaptive-update.md) | 中文

## 问题

DSH 仍是早期预览产品，上游变化可能同时让包结构、Client 合同、Profile 组装、持久化假设和本地插件失效。直接把这些变化应用到正在运行的工作区，会让产品在冲突尚未理解或修复时就无法使用。

## 决策

Web Profile 内置一个名为 `@deepseek-ai/dsh-client-ui-adaptive-update` 的原生 Host + Client 插件。设置入口和页面标题都是**持续适配**。用户主动操作时，系统锁定一个官方提交，并把长时间工作交给能够独立存活于当前 DSH 进程的外部工人。

页面中的**自动更新 · 每 6 小时**胶囊会把用户主动开启的偏好持久化到 DSH Home 之外。开启后立即开始检查官方分支，此后每六小时检查一次。本地 `HEAD` 已经包含的官方提交不会触发操作；新提交复用主动按键的同一个外部事务，定时调度不另造第二套更新实现。

外部工人在可丢弃工作树中执行一次真实试合并并计算准确的 Git 冲突，不发起语义深审。工人删除该工作树后，在独立候选区重复锁定合并；Git 能自动解决时完全跳过模型。存在冲突时，一次有界的稳定版 Headless Agent 调用只接收冲突文件和直接受影响的插件，在不提交、不修改真实 DSH Home 的前提下解决候选版本。

候选版本必须没有未解决合并项，准备锁定依赖，并通过一次生产构建。一次构建失败最多返回一次窄范围 Agent 修复，然后再执行一次构建。更新器回归、独立全仓类型检查、Web 回放和切换前影子启动都不属于产品更新链路。冲突处理和构建阶段不会修改当前工作区和用户数据。

## 切换事务

验证通过后，外部工人提交候选版本，等待所有根 Agent 空闲，停止当前运行时，创建一份 DSH Home 写时复制快照，并把干净工作区前进到候选提交。候选版本必须让 Host 页面和 Client 资源同时可访问。启动失败时，工人会在重新启动旧运行时前恢复上一个 Git 提交和数据快照。

操作状态以原子方式持久化到 DSH Home 之外的插件自有同级目录。后续插件实例可恢复被中断的应用阶段：已就绪的候选版本完成操作，其他状态恢复上一个提交和快照。

## 保留与隐私

冲突处理只把稳定 Agent 必需的配置文件复制到私有 Home。会话、附件、工作区和其他用户数据始终留在真实 Home。源码历史由 Git 对象保留；成功清理会删除审查、候选、私有 Agent Home 和日志产物，最多留一份上一版写时复制数据快照。

## 考虑过的替代方案

**在当前工作区合并上游。**这无法在修复冲突、依赖变化和启动失败时保持产品可用，因此一次失败编辑就可能让整个 DSH 进程崩溃。

**不提供开关，始终在后台更新。**强制定时监控会让用户失去对网络检查和源码变化的控制。持续适配由用户主动开启并持久保留明确选择，切换前仍然等待对话空闲。

**每次更新都做语义深审和穷举回放。**这能最大化本地证据，但会让普通上游合并耗时数小时。当前链路把 Agent 工作限制在真实冲突，并以一次生产构建作为兼容边界；切换时仍保留就绪检查和回滚。

**每个版本保留一个完整产品目录。**完整复制会让保留空间每个版本增加数百 MB。Git 历史、可丢弃工作树和一份写时复制数据快照可以提供回滚，不需要永久版本目录。

**在运行进程内修补 Loader 状态。**包、Host、Client 和持久化变化没有同一个可逆的进程内边界。外部候选区和重启事务把不确定工作留在被保护的进程之外。

## 后果

用户可以主动更新或选择六小时监控，并在冲突处理和构建期间继续使用旧版本。活跃对话会延后短暂切换，对话和附件存储在更新过程中保持权威。干净合并不调用模型；存在冲突时使用一次有界请求，构建修复最多再使用一次。速度优先意味着放弃切换前的穷举行为回放，但生产构建、启动就绪检查、源码回滚、数据回滚、有界临时候选区和一份写时复制快照仍覆盖常见恢复路径。
